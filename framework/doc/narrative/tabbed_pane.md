# tabbed_pane (narrative)
spec は [../tabbed_pane.md](../tabbed_pane.md) である。ここには設計判断の理由を残す。

## 型定義
`TabbedPane` は `SplitPane` と同じ埋め込み `Container` 方式にした。タブペインは内容を
複数持つコンテナであり、内容の所有と破棄は既存の `Container.deinit` の考え方に合わせるのが
もっとも自然である。公開 `Component` を別に持たず、先頭の `container.component` を公開面にすることで、
親レイアウトやテーマ適用、イベント委譲の扱いも既存コンポジットと同じになる。

内容の表示、非表示にはゼロ境界を使う。可視フラグを新設しない理由は、既存のイベント hit-test と
レイアウトが境界を真実として扱っているためである。非選択内容を `(0, 26, 0, 0)` に置けば、
描画と入力の両方から自然に外れる。

## 関数定義
`addTab` はタイトルを複製し、内容の所有権を必ず受け取る。これは `SplitPane.create` が
失敗時にも渡された pane を破棄する契約と対称である。タブ追加の途中でタイトル確保や子追加に失敗しても、
呼び出し元が内容を後始末しなくてよい。

`removeTab` は内容を破棄する。タブペインから外した内容を呼び出し元に返す API は v1 には置かない。
所有の向きが単純なほど、`Container.deinit` と同じ寿命規則で理解できるためである。
内容を差し替えたい場合は、新しい内容を追加して古いタブを削除する。

選択通知は `ChangeListenerList` にした。`List` と `Table` が選択変更を `ChangeEvent` として扱っており、
タブ選択も同じ種類の状態変更である。イベントは選択 index そのものを持たず、受け手が
`getSelectedIndex` を読む形にする。これも既存のモデル通知に合わせた設計である。

## 利用例
典型的な使い方では、設定画面や詳細ペインのように数枚の固定ページを切り替える。
各ページは普通の `Panel`、`ScrollPane`、`SplitPane` などでよい。`TabbedPane` はページの中身を解釈せず、
選択中のコンポーネントに領域を渡すだけである。

タブ列の高さや水平 padding は theme ではなく定数にした。現行 theme は色だけを扱っているため、
寸法トークンをここで追加すると theme の責務が変わる。見た目の寸法を拡張する段階で、
theme 全体の設計と合わせて再検討する。

## 機能要望
* タブの閉じるボタン
* 下端、左端、右端のタブ配置
* キーボードによるタブ移動
* タブ列のスクロールまたは overflow 表示
* ドラッグによるタブ並べ替え
* タブアイコン
