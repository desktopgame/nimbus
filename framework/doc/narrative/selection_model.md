# selection_model (narrative)
spec は [../selection_model.md](../selection_model.md)。 ここには設計判断の理由を残す。

## 独立モジュールにして List / Table で共有した理由
選択の状態と遷移ロジック (トグル・範囲・モード畳み込み) は List と Table で完全に同じ。
各ウィジェットにインラインで持つと同じロジックを 2 箇所に複製することになる。
ListModel を両者で共有しているのと同じ考えで、 選択も共有型 1 つに寄せた。
ウィジェットは `selection` フィールドに持ち、 入力ジェスチャを操作へ翻訳するだけになる。

却下案: 各ウィジェットにフィールドを直接持つ。 新モジュールは増えないが、 複製が drift の元になる。

## 既定を `.single` にした理由
既存の List / Table は単一選択で、 多くの利用箇所がそれを前提にしている。
既定を `.single` にすれば、 それらは一切変更なしで従来どおり動く。
複数選択が要るウィジェット (ファイラー) だけ `setSelectionMode(.multiple)` でオプトインする。
`.single` ではモデル側がどの操作も 1 行に畳むので、 ウィジェットはジェスチャを出し分けなくてよい。

## 単一選択 API を温存した理由
`getSelected` / `setSelected` は多くの呼び出し側が使っている。
複数 API へ一本化すると app_filer をはじめ全 consumer を書き換えることになる。
そこで単一 API は「lead を返す / その 1 行だけ選択する」という意味で温存し、
`getSelectedIndices` などの複数 API を足す形にした。 既存コードは無改修で動く。

## 変更操作が bool を返す理由
GUI では「変わっていないのに通知・再描画する」のを避けたい。
操作が「実際に変化したか」を返せば、 ウィジェットは変化時だけ ChangeEvent と再描画を出せる。
List / Table の `applySelectionChange(changed)` がこの分岐を一手に引き受ける。

## モデル変更で index をずらさない理由
データモデルの挿入 / 削除に追従して選択 index を正確にずらすには、
変更通知が「どこに何行挿入 / 削除したか」を持つ必要がある (現状の通知は粒度が粗い)。
v1 は従来の単一選択と同じ割り切りで、 範囲外になった index を捨てるだけにした。
ファイラーはリネームや削除のあと選択し直すので、 これで実用上困らない。
細粒度の変更通知が入ったら index ずらしを足せる (spec の機能要望)。
