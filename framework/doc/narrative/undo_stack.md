# undo_stack
UndoStack の立ち位置、Command を型消去する理由、上限付きスタックの退避、合体 (tryMerge) の扱い、リスナーが遷移時だけ発火する理由。

## 誰が使うか
`UndoStack` は特定のデータ構造に結び付かない汎用のアンドゥ/リドゥプリミティブである。
現状これを組み立てて使う唯一の利用者は `EditableText` (`editable_text.md`) で、テキスト置換を `Command` として積んでいる。
とはいえスタック自体はテキストを何も知らないので、可逆な操作であれば描画状態・モデル編集・レイアウト変更なども同じ仕組みに乗せられる。
`Command` の vtable が拡張点であり、新しい可逆操作を足したい側がそれを実装する。

## Command を型消去する理由
スタックは中身の操作が「何をするか」を知る必要がない。必要なのは「やり直す」「元に戻す」「捨てる」の 3 つだけである。
そこで `Command` を `vtable` + `ctx` の型消去ペアにして、操作固有の状態は `ctx` の先に閉じ込めた。
これにより 1 つのスタックへ種類の異なる操作を混在させられ、スタック側は操作の実体に依存しない。

`tryMerge` / `displayName` を必須にせず省略可 (既定 `null`) にしたのは、コストを払う操作だけが払う設計にするためである。
合体もラベル表示も要らない単純な操作は 3 つの必須関数だけ書けばよく、余計なフックの実装を強制しない。

## 上限付きスタックと退避
アンドゥ履歴を無制限に持つとメモリが際限なく増える。そこで保持数に上限 (`default_limit` = 200、`initWithLimit` で変更可) を設けた。
上限を超えて新しいコマンドを積むと、最古のコマンドから順に `deinit` して落とす。
このとき `index` (アンドゥ/リドゥ の境界) も同じだけ手前へ詰めるので、落とした古い手を指したままになることはない。
落とすコマンドは必ず `deinit` を通すため、`ctx` の内部確保物もリークしない。

## 合体 (tryMerge) の扱い
`push` はまずリドゥ側の未来 (`[index, list.len)`) を捨ててから積む。分岐したリドゥ履歴は破棄するという普通のアンドゥの意味論である。
次に直前のコマンドへ `tryMerge` を試す。直前が受け入れたら、新しいコマンドは合体先に取り込まれて自身は `deinit` され、スタックは伸びない。
合体を受け入れるかどうかの判断はコマンド側にあり、スタックは結果の真偽だけを見る。
テキスト編集での「連続タイプを 1 手にまとめる」判定は `EditableText` 側の `Command` が実装しており、`UndoStack` はその方針を知らない。

## エラー時に index を戻す
コマンドの `undo` / `redo` は `anyerror!void` を返せる。途中で失敗したときにスタックの `index` だけ進めてしまうと、状態とカーソルがずれる。
そこで `undo` は失敗したら減らした `index` を元へ戻し、`redo` は成功するまで `index` を進めない。
これにより「操作が失敗したら履歴カーソルも動かない」という一貫性を保つ。

## リスナーが遷移時だけ発火する理由
`addCanChangeListener` の主な用途はアンドゥ / リドゥ ボタンやメニュー項目の enable 切り替えである。
enable の状態は `canUndo` / `canRedo` の真偽でしか決まらないので、その 2 値が変わらない操作でリスナーを呼んでも受け手は同じ再計算を繰り返すだけになる。
そこで `push` / `undo` / `redo` / `clear` の前後で `canUndo` / `canRedo` を比べ、**どちらかが変化したときだけ**発火する。
たとえば「上限に達したスタックへさらに積む」ケースは、`canUndo` も `canRedo` も真のまま変わらないので発火しない。
