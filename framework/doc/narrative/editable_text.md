# editable_text
EditableText の立ち位置、書記素クラスタ境界を集約する理由、アンドゥのコアレッシング、改行正規化、OOM の all-or-nothing 保証。

## 誰が使うか
`EditableText` は単体で画面に出るウィジェットではなく、テキストウィジェットの土台となる編集コアである。
現状の利用者は `TextField` と `TextArea` の 2 つで、それぞれが `core` フィールドとして 1 つ内包する。
将来テキスト入力を伴うウィジェット (検索ボックス、インライン編集セルなど) を足すときも、このコアを載せれば編集の意味論を揃えられる。

描画・クリップボード I/O・IME 描画・画面行モデル・スクロール連携はウィジェット側の関心なので、コアには持たせない。
コアが持つのは「バイト列・キャレット・選択・アンドゥ/リドゥ」という論理状態だけである。

## 依存関係
バイト列の保持は `GapBuffer` (`gapbuffer.md`) に、アンドゥ/リドゥ は `UndoStack` (`undo_stack.md`) に委譲する。
書記素クラスタ境界の計算は `awt.grapheme` に委譲する。
`EditableText` はこれらを 1 つにまとめ、ウィジェットからは「編集操作 1 つ = メソッド 1 つ」で扱えるようにする層である。

## 境界計算を 1 か所に集める理由
CLAUDE.md「書記素クラスタ」は、初版はコードポイント単位で妥協しつつ、書記素クラスタ単位へ簡単に移行できる実装を求めている。
`prevBoundary` / `nextBoundary` / `snapToBoundary` の 3 つにキャレット移動とスナップを集約したことで、境界の定義は 1 か所に閉じた。
現在この 3 つは `awt.grapheme` の UAX #29 ベースの実装を呼ぶので、ウィジェット側のコードは境界の中身を知らずに済む。
`TextField` と `TextArea` はこのコアを共有するため、片方だけ挙動がずれることがない。

## アンドゥのコアレッシングの方針
文字を 1 つずつ打つたびにアンドゥ単位を作ると、`Ctrl+Z` が 1 文字ずつしか戻せず使いにくい。
そこで隣接する「1 書記素クラスタの挿入」どうしは 1 つのアンドゥコマンドへ合体させる。合体できるのは以下をすべて満たすときに限る。

* 直前のコマンドが「選択なしの単一クラスタ挿入」で、改行を含まない。
* 次のコマンドも同じく単一クラスタ挿入で、直前の挿入の直後に連続している。
* 両者の `merge_generation` が一致する (あいだで区切りが入っていない)。

`merge_generation` は `breakCoalescing` で進む世代カウンターである。
キャレット移動・選択変更・削除・貼り付け・アンドゥ/リドゥ・IME クリアの節目で、ウィジェットが `breakCoalescing` を呼ぶ。
すると世代が変わり、以降の入力は前の挿入と合体しなくなる。
これにより「連続タイプは 1 手、方向転換したら別の手」という自然なアンドゥ粒度になる。

## 改行の正規化
`initFromSlice` / `setText` / `applyEdit` に入るバイト列は、`\r\n` と `\r` をすべて `\n` へ畳んでから取り込む。
内部に `\n` しか現れない前提を置けるので、`TextArea` の画面行モデルや `lineStartAtByte` の走査が単純になる。
貼り付けや外部ファイル読み込みで CRLF が混ざっても、コアに入った時点で 1 種類に揃う。

## OOM の all-or-nothing
`applyEdit` は編集の途中でメモリ確保に失敗しても、テキスト・キャレット・アンドゥスタックを操作前の状態に保ったまま `error.OutOfMemory` を返す。
先にアンドゥコマンド・バッファの確保を済ませてから (`ensureUnusedCapacity` / `ensureReplaceCapacity`)、確保が全部通ったあとに一気に反映するためである。
呼び出し側は失敗しても後片付けが要らず、状態の一貫性も保たれる。
この不変条件は `checkAllAllocationFailures` を使った allocation-failure テストで守っている。
