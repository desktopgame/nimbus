# theme
Theme（既定 LAF の色カタログ）の設計判断と却下案の記録。
仕様は [../theme.md](../theme.md)、起票と棚卸しの経緯は
`{REPO_ROOT}/doc/internal/framework_backlog.md` #4。

## LAF と Theme の線引き
このプロジェクトにおける用語の定義:

> **LAF（ルックアンドフィール）とは vtable 一式の差し替え**である。
> 座席は既存の `Component.setVTable`（component.md「VTable の差し替え」の「一斉差し替え」）のみで、
> 新しい委譲機構は作らない。
> **Theme は既定 LAF のパラメータ**であり、かつ public な公開型である。

フル LAF（形状・描画手順ごと変える）を書く者は、既定 vtable をコピーして paint を
差し替える（widget_listdnd 等で実証済みのデコレーションパターン）。その paint が
`component.theme` を読めば配色はアプリのテーマ設定に追従するし、読まなくてもよい —
Theme は公開基盤であって契約ではない。

## 却下案: ComponentUI 風の委譲機構（Swing 流フル LAF）
ウィジェットごとに UI delegate を持たせ、LAF をその差し替えとして表現する案。却下した。
- 差し替えの座席は vtable として既にあり、**二つ目の差し替え機構**になる。
- delegate は関数ポインタの束 = **Zig コードを書ける人にしか触れない拡張軸**。nimbus の
  将来像は C ABI 経由の Python / JS 利用者であり、「見た目のカスタマイズに Zig が要る」
  機構をこれ以上厚くしない。
- Swing のフル pluggable LAF 自体、振り返れば過剰装置だったというのが大方の総括。
  現実の需要の大半は「ダークモード」「ブランド色」= 値の差し替えで足りる。

## 却下案: 文字列キーの Map（Swing UIManager 方式）
`"Button.background"` のような文字列キーで任意の値を持てる開いた Map。却下した。
- typo が**黙って既定値にフォールバック**する（UIDefaults の有名な地獄）。固定 struct なら
  コンパイルエラー。
- スキーマの非発見性: 「何が変えられるか」の全量がどこにも書かれず、LAF ごとに非互換に
  なったのが Swing の実史。固定 struct は定義 1 か所が全量。
- 値が variant 型になり取り出しキャストが要る。固定 struct は Color は Color。
- 「開いている」利点の買い手がいない: カスタムウィジェットがやるべきは独自キーの発明では
  なく既存の役割トークンを読むこと（それでテーマ切替に追従する）。独自の調整値は自分の
  struct に持てばよい。
- 仮に開いたキーの実需が出ても、`extras` の Map フィールドを**後から additive に足せる**。
  逆方向（Map → struct）は破壊的なので、閉じた側から始めるのが安全側。

Flutter の `ColorScheme`（固定クラス、役割トークン約 30 個）+ ウィジェット別 ThemeData
という構成が同型の前例。

## 参照方式: ファクトリ DI に決めた理由
`Application` がテーマを 1 個所有し（値コピー）、各ファクトリが生成時に
`component.theme = &app.theme` を注入する。
- 都度取得（paint 時に root プロパティを lazy walk / Graphics 経由で配る）はコストと
  配管が増えるだけで、テーマが**起動時固定**ならポインタ 1 本の注入で同じ結果になる。
- `Component.theme` の既定値は comptime 定数 `&Theme.default`。ファクトリを通らない
  直接 `create` も既定テーマで描けるため、**全 create シグネチャの変更も呼び順の罠も
  発生しない**。
- ライフタイム: コンポーネントが指すのは Application 内のコピーで、Application は
  全ウィジェットより長生き。ダングリングは構造的に起きない。
  `initWithTheme` が値コピーするのは「init に渡した一時変数が先に死ぬ」罠を消すため。

## 実行中切り替えを非対応にした理由
テーマは起動時固定。切り替えはアプリ再起動で行う（作者決定）。
色だけなら実行中の変更も repaint で済むが、メトリクスを含めた瞬間に破綻する:
nimbus のウィジェットは `applyMetrics` が **min_size を生成時に焼き込む**設計のため、
実行中のテーマ差し替えには全ツリーの re-metrics + 再レイアウト
（Swing の `updateComponentTreeUI` 相当の無効化プロトコル）が必要になる。
あれこそが「実行中に LAF を更新すると描画が壊れる」の正体であり、起動時固定の宣言に
よってこの設計問題ごと消した。実需が出たら無効化プロトコル込みで別途起票する。

## 却下案: per-component の差分テーマ / カスケード
CSS 的な「子は親のテーマを継承し差分だけ上書き」。無駄に複雑になるだけなので不採用（作者決定）。
- 点の上書きは既存の per-widget フィールド（Button の `color` / `font` 等）の仕事。
- サブツリー単位の別テーマは、`theme` が public フィールドである以上、利用者が自分で
  差し替えれば**機構ゼロ**で可能。フレームワークはカスケード規則を持たない。
- なお「差分だけ書きたい」はテーマ**定義**側では成立している: 全フィールドに既定値が
  あるため、`Theme{ .accent = ... }` と書けば残りは既定のまま。

## 命名がハイブリッド（役割別 + ウィジェット別）である理由
直書き色の全棚卸し（約 28 種）で 2 つの事実が出た:
- **同じ RGB が別の意味で使われている**: `(1,1,1)` は入力欄背景でもありアクセント上の
  白文字でもある。`(0.55³)` は disabled テキストでもあり入力欄ボーダーでもある。
  ダークテーマで挙動が分かれるため、値の重複排除ではなく**意味の割り当て**として
  別トークンに分離する必要がある（役割別が必要な理由）。
- **意図的に役割から外れた色がある**: Button の押下背景は menu の押下背景（accent）より
  意図的に淡い。役割に畳むと見た目が変わる（ウィジェット別が必要な理由）。

よって「役割別を基本に、畳めない箇所だけウィジェット別」のハイブリッド。
既定値の統一判断（黒 2 種 → `text` 等、全 6 件は backlog #4 参照）は実装時の
snapshot 差分画像で 1 件ずつ作者が承認 / 却下する。
