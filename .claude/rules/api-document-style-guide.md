# api-document-style-guide
データ構造、シグネチャ、ライフタイムを記述するドキュメントについてのスタイルガイドです。

## ドキュメントの種別
ドキュメントは spec と narrative の 2 種類に分かれる。
同じモジュールの spec と narrative は同名ファイルにする (例: `event_queue.md` と `narrative/event_queue.md`)。

### spec (`{レイヤー}/doc/{モジュール}.md`)
型定義・関数定義 (シグネチャ・事前条件・診断情報) を中心とした、機械的にチェック可能な内容を置く。
配置可能な `##` 見出しは後述のテンプレートに列挙されたものに限定する。

ここでの「レイヤー」は `awt` / `awt-c` / `framework` のような nimbus の上位構成単位を指す
(CLAUDE.md「リポジトリ構成」参照)。
「モジュール」は 1 つの構造体とそれに紐づく関数群、つまり多くの場合 1 ファイルにまとまる単位を指す。

### narrative (`{レイヤー}/doc/narrative/{モジュール}.md`)
spec に置けないもの (「なぜそうしたか」「却下案」「設計史」「複数項目にまたがる解説」など) を置く。
見出しは自由。

### どちらに書くか迷ったら
- 型・シグネチャ・1 関数の契約 → spec
- 「なぜ」「ほかの案ではなぜダメか」「複数関数にまたがる解説」 → narrative

spec を書いていて allow-list 外の `##` 見出しを足したくなったら、それは narrative 行きの合図。

## フロントマター
spec / narrative 両方とも `unsafe` フラグを持つ。

```yaml
---
unsafe: true
---
```

`unsafe: true` は「AI が編集したのち、人間がチェックしていない」状態を意味する。
AI が編集すると自動で `true` になる (./claude/settings.jsonのhooksを参照)。
人間が読んで問題なし、または書き直したら `false` にする。

このフラグはチェック作業の負荷軽減 (どこを優先的に見るべきか) のために使う。

## spec のテンプレート
基本的には以下のようなフォーマットになる。
`##` 見出しはここに列挙されたもの (`型定義` / `関数定義` / `利用例` / `機能要望`) に限定する。
`## 関数定義` 配下の `###` 見出しは関数固有の補足 (`### 失敗時の保証` など) として自由に追加してよい。

```md
# モジュール名
モジュールについての簡潔な説明を1~2行以内で述べる。
モジュールとは、構造体とそれに紐づく関数の一覧からなる、多くの場合一つのファイルにまとめて定義される機能群を指す。

## 型定義
構造体の定義を示す。

## 関数定義
見出しは関数の名前ではなく実行する処理を簡潔に記述する。
`バッファの生成`、 `バッファの破棄`など。
シグネチャを見出しの次の行に記述する。

一行空行を開けて、処理の内容を記述する。
処理の内容について言及するとき、型名、関数名、引数名はクォートして表記する。
例えば、`typeName`、`funcName`、`argName`のように表記する。

実装の中身（関数本体のコード）は記述しない。
契約として「何をするか」だけを書く。
処理のアルゴリズムや内部状態の操作はソースコメントの領分。

### 事前条件
関数を呼び出す前に満たさなければならない条件を記述する。オプショナル。
もし条件を満たしていなかった場合どうなるかを記述する。UB（undefined behaviour）でも可。
逆に、この条件を満たしているときは正常に動作することが保証される（＝それ以外はUB）という書き方も可。

### 診断情報
不正な状態、不正な引数で関数が実行されたときに出力するログ内容を記述する。オプショナル。

---

(関数定義セクションが複数並んだあと、最後の関数定義のあとに `---` を入れて区切る。
これより下に利用例セクションなどが続く。)

## 利用例
サンプルコードをここに集約する。オプショナル。
関数ごとに散らさず、現実的な呼び出しフローを 1〜2 個示す。
モジュールの全体像を素早くつかむために有用。

ある関数に固有の非自明な呼び方は、当該関数の説明内にミニスニペットを置いてよい（例外）。

## 機能要望
現在のソースコードには含まれていないが、将来のバージョンで実装する可能性のある機能があれば、言及する。オプショナル。
```

## narrative の指針
narrative は自由フォーマットだが、見出しの命名は具体的にする。
抽象的な見出しは避ける。

例:「立ち位置」よりも「依存関係」が適切。

悪い例:
```md
## 立ち位置
- レイヤー: **awt 層**（`programs` + `UniformBuffer` + `CommandBuffer` の上に乗る）
- 利用者: framework 層の `Component.paintComponent(Graphics)` など
- 内部実装: `awt.programs.Text` / `Color` / `Image` を使い分けて draw を発行する
- framework 側から見ると awt-c や個別 program の存在は見えない
```

改善例:
```md
## 依存関係
`awt-c` に依存し、その低レベルなグラフィックス機能を隠蔽して抽象的な機能として提供する。
例えば、`drawRect`、 `fillRect` など。
```

## 用語
ドキュメント中で以下は事前に定義なく使用できる。

### UB
`undefined behaviour` の略。未定義動作を指す。

## 表記の統一
型定義、関数定義、引数名以外の箇所では明示的に日本語で表記することがある。
基本方針として、一般的な技術概念（グラフィックスに限らない）はカタカナ、特定の API (DX12 など) に固有の用語は英語のまま残す。

代表例: `vertex` → 頂点、`buffer` → バッファ、`widget` → ウィジェット、`window` → ウィンドウ。
統一する語の一覧は `tools/textlint/prh.yml` が一次情報で、`npm run lint` で検出でき `--fix` で自動修正できる。
ここにベタ列挙はしない（同じ表を 2 か所に置くと drift するため）。

### 型名と一般概念は大文字小文字で分ける
同じ語が型名でもあり一般概念でもあることがある（Window / Event / Model など）。
PascalCase は型を指し、小文字の英語形は一般概念を指す。
例えば `Window` は型、ウィンドウ（や小文字 window）は概念。
prh は小文字形だけをカタカナに直す。
よって narrative では型名をそのまま `Window` と書けばよく、バッククォートで囲む必要はない。
（関数定義の説明文ではクォート必須。「関数定義」を参照。）

### 例外（綴り統一だけでは足りない注記）
綴りの対応は prh が機械的に直すが、次のような「書き手の判断が要る」ものは prh では表せないので明記する。

* DirectX12 の `static sampler` はそのまま `static sampler` と英語で表記する。
* `scissor` はシザー / シザー矩形のどちらでもよい。

## 文体
「ですます調」ではなく、「だ・である調」で統一する。

## その他
作者の好みにより、英単語の前後にスペースを空けることがある。
例えば、以下のように。

```
このドキュメントは `nimbus` のAPIについて記述しています。
```

これについては明確なルールはないので、守っていてもいなくても構わない。
気になったときに作者が自分で直す。
