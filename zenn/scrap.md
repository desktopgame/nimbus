設計判断についてのメモ

Swing には Application 型がありません。
私は Swing のこの設計が好きだったのですが、よくよく調べていくと Application 型を提供するべきだと思いました。

例えば、
* Qt なら QApplication クラスがある
* wxWidgets なら wxApp クラスがある
* GTK なら GtkApplication クラスがある

で、実は Swing 、というか Swing Application Framework （これは結局頓挫したっぽいのですが）も Application クラスを提供しています。

これのメリットは、本質的にグローバルなものの置き場所を用意できる、ということでしょうか。
イベントキューやアロケーターなど、グローバルにいろんなところから触りたいものの置き場所にできます。
こういう置き場所がないと、グローバル変数として置いといて直接依存することになります。 java.awt.EventQueue などが実際そうですが。

メニューの自前描画について

Swing においてはメニューバーに好きなコンポーネントを入れられます。

JMenuItemの内部にJButtonを配置する
https://ateraimemo.com/Swing/ButtonsInMenuItem.html

一般的なユースケースではない気がしますが、これをどうサポートしたらよいのかについて。
ポップアップメニューがクライアント領域をはみ出さないならそのまま描画すればいいはずです。

でも netbeans は（参考にすべき動作としてベンチマークにしてるのですが）ポップアップメニューがウィンドウをはみ出すことがあります。
この場合は装飾無しウィンドウを出すしかないと思われます。

ところでメニューと言えば、Swing はメニューバーをクライアント領域に描画するようです。

コンポーネントの座標系について

Swing ではコンポーネントの座標は親Bounds内におけるローカル座標。
しかしこれだと問題があり、ウィンドウやダイアログもコンポーネントなのです。

でも、ウィンドウやダイアログはルートのコンポーネントなので、少し座標の意味が違ってきます。
モニターが親Boundsであるとするなら矛盾はしないのですが。

nimbus ではどうしてるのかというと、ウィンドウの画面上のBoundsとコンポーネントのBoundsを区別してどちらも保持しています。
なぜかというと、ウィンドウにはメニューバーという既存のレイアウトの枠組みに収まらないコンポーネントがあるからです。
レイアウトの自由度がない（ある方が困る）し、メニューを開くとメニューバーのサイズに縛られず下のコンポーネントを覆うように展開される。
こうした理由で通常のレイアウトの外に出しています。

コンポーネント座標が原則として親Bounds内のローカル座標で一貫するためには、
ウィンドウのコンポーネントとしてのBoundsはメニューバーの分だけオフセットされる必要があります。

つまり、
x: 0
y: menu_bar_height
w: window_width
h: window_height - menu_bar_height
これがウィンドウの正しいBoundsになります。（メニューバーがないときは menu_bar_height=0）

:::message
メニューバーが特別扱いされていなかったら、単にこれで済みます。
x: 0
y: 0
w: window_width
h: window_height
:::

そして、ウィンドウのBoundsはプログラムからセットしたときだけではなく、
ユーザーが勝手に動かしたりリサイズしたときにも変わるので、双方向の同期が必要です。
