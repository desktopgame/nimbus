## #8 パンくずリスト（パスバーの発展形）
- 状態: 棚上げ
- 優先度: 中
- 影響範囲: app_filer（ツールバーのパスバー周辺。パス要素ごとのボタン列 + パンくず↔テキスト編集のトグル）
- 更新日: 2026-06-14
- 依存: #3（編集できるパスバー・完了済み）

### 何
#3「編集できるパスバー」の発展形。Explorer 風に、パスを区切り（`/`）ごとのクリック可能な要素として
表示し、要素をクリックするとその prefix（その要素までのパス）へ移動できるようにする。加えて Windows 式の
ハイブリッド、すなわち**パンくず表示の空き領域をクリックするとテキストフィールドに化けて**パスを直接
編集できる（編集を抜けるとパンくず表示に戻る）挙動を持たせる。#3 の TextField 入力 → Enter 移動は
そのテキスト編集側として既に動いているので、本項目は「表示をパンくず化する」「両モードを切り替える」分。

### なぜ（保留理由）
point-of-need。#3 で絶対パス入力 → Enter 移動はできており、当面の移動操作は足りている。
パンくずは UX 向上であって新しい移動能力ではないため、実機を触って「クリックで途中階層へ飛びたい」が
痛みとして出てから着手するのが安い。

### 候補アプローチ
- パス要素ごとのボタン列: 現在パスを区切りで分割し、要素ごとにボタン（またはフラットボタン）を並べる。
  各ボタンのクリックでその要素までの prefix を組み立てて `loadDir(prefix)`。区切り記号も要素間に描く。
- パンくず表示 ↔ テキスト編集のトグル: パンくず（ボタン列）とテキスト編集 field を切り替える。
  編集 field は #3 で既存。切り替えは app_filer 内に既にある CardLayout レシピ（list / details ビューの
  ホルダーで使っている `CardLayout`）をそのまま流用でき、機構の新設は不要。空き領域クリックで編集へ、
  Enter / フォーカス喪失でパンくず表示へ戻す。

### 決めること
- パンくず ↔ 編集の切り替えトリガ（空き領域クリックのみ / 専用ボタン / 末尾要素クリック）。
- 長いパスがツールバー幅を超えたときの扱い（先頭省略 `…` / 横スクロール）。
- 区切り要素を押せるドロップダウン（兄弟フォルダ一覧）まで入れるかは将来 — 初版はクリック移動 + 編集トグルに絞る。

### 完了条件
パンくずの各要素をクリックしてその階層へ移動でき、空き領域クリックでテキスト編集に切り替えて
#3 同様に絶対パス入力 → Enter 移動ができる（両モードを行き来できる）。

## #9 app_filer の理論上エッジケース（低優先 follow-up まとめ）
- 状態: 棚上げ
- 優先度: 低
- 影響範囲: app_filer（パスバーの祖先キーバインド下の編集 / 詳細ビュー DnD）
- 更新日: 2026-06-14
- 依存: #3（パスバー）/ framework#16（Table の DnD 用 y→行アクセサ）

### 何
今セッションで出た、app_filer の DnD / 編集まわりの理論上エッジケースをまとめて記録する。
いずれも実運用ではほぼ到達不可で実害は観測されていない。過剰に細分化せず 1 項目に束ねる。
- パスバーの IME 変換中 Backspace が祖先 `goUp` に抜け得る。Backspace はウィンドウ全体に
  `Filer.onBackspace`（= `goUp`、親フォルダへ移動）をバインドしている。パスバーの TextField が
  preedit（IME 変換）中に Backspace を consume しないと、破壊的な祖先バインドへ抜けて意図せず
  ディレクトリ移動が起き得る。consume の有無はプラットフォーム依存。パスバーのような破壊的な
  祖先バインド下に編集フィールドを置いたときの既知のエッジ。
- 詳細ビュー DnD のドラッグ中にビュー切替が起きると `activeRowAt` / `activeFilesComponent` と
  `Transfer.source` が食い違う理論上の懸念。ドラッグ開始時に `source = activeFilesComponent()` を
  焼き込む一方、`filesOnOver` / `filesOnDrop` は `activeRowAt`（= 現在の `view_mode` に依存）で
  行を引くため、ドラッグ中に list ⇄ details を切り替えると両者がずれ得る。実運用ではドラッグ中に
  ビュー切替操作は到達しにくい。

### なぜ（保留理由）
2 件とも実害が観測されておらず（通常 IME 入力で破壊的移動は踏みにくい、ドラッグ中のビュー切替は
ほぼ起きない）、point-of-need。まとめて記録だけ残す。

### 完了条件
着手した項目について、preedit 中の consume / ビュー切替時の DnD 整合が手当てされ、挙動を確認できる。
本項目には未着手分を残す。
