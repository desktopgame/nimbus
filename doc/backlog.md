# バックログ運用規約
後回しにした作業・検討中の項目を、再現可能なかたちで記録・追跡するための共通ルール。
領域を問わず適用する（C ABI 生成・レイアウト・描画・ビルドなど、どの分野のバックログにも使う）。

バックログの目的は、判断とその理由を**未来の自分や他の作者・実装者が辿れる状態**で残すこと。
「なぜ後回しにしたか」「再開時に何を決めればよいか」がその場で分かるようにする。

## 置き場所と粒度
- バックログは領域ごとに分け、`doc/<領域>_backlog.md` に置く（例: `c_api_codegen_backlog.md`）。
- 1 ファイルに 1 領域。横断的な作業は関連する領域のバックログに相互リンクで残す。
- 実例: [c_api_codegen_backlog.md](c_api_codegen_backlog.md)。

## 作業項目の番号（ID）
各項目に安定した参照 ID を振る。ID の唯一の役割は **identity（あとから「#4 を直して」で同じものを指せる）**。

- **起票順の連番** `#1` `#2` … を振る。**あとから番号がずれない・使い回さない**。
- **欠番を許容する**。完了・却下しても番号は残し、欠番のまま詰めない（状態は `状態:` フィールドで表す）。
- **番号には優先度・状態・順序などの情報を込めない**。それらはメタ情報フィールドに置く
  （番号に意味を込めると、変わるたび採番し直しになり参照が腐る）。
- **子項目は文字サフィックス 1 段だけ** `#6a` `#6b`。**2 段以上はネストしない**
  （`#6a-2` のような深い構造は作らない）。親 `#6` はテーマ見出しでも本体の作業項目でもよい。
- 子にするのは「**1 つの親を同時に分割した兄弟**」のときだけ。「独立だが順序があるだけ」のものは
  別番号にして `依存:` フィールドで関係を表す（深い関係は ID ではなく依存で書く）。
- ファイルをまたいで参照するときだけ、短い領域接頭辞を付けてよい（例: `capi#4`）。ファイル内は素の `#4`。

## 作業項目のテンプレート
1 項目は見出し＋メタ情報＋本文で書く。メタ情報は必須。本文は項目の性質に応じて取捨する
（後回し・要検討の項目ほど「なぜ / 候補 / 決めること」を厚く、単純な未着手は薄くてよい）。

```
## #<番号> <作業項目のタイトル>
- 状態: 未着手 | 設計確定 | 実装中 | 完了 | 却下 | 棚上げ
- 優先度: 高 | 中 | 低
- 影響範囲: <どのモジュール / ファイル / 利用者・エンドユーザーに影響するか>
- 更新日: YYYY-MM-DD
- 依存: <先に片付ける必要がある項目 / なし>

### 何
やりたいこと・対象。データ構造やシグネチャが絡むなら明記する。

### なぜ（保留理由）
なぜ今やらないか / なぜ単純な方法で出せないか。完了済みなら省略可。

### 候補アプローチ
取りうる実装方針（複数あれば併記し、トレードオフを一言添える）。

### 決めること
着手前に作者が確定すべき点（所有権・寿命・スコープ・規約の選択など）。
ここが埋まると実装に入れる。

### 完了条件
何をもって完了とするか（検証手順を含む）。
```

### メタ情報フィールドの規約
- **状態**: 上記のいずれか。`却下` は「やらないと決めた」ことの記録（理由も残す）。
- **優先度**: 高 / 中 / 低。「いつか」は低。影響範囲の広さと実需の有無で決める。
- **影響範囲**: 触る範囲を具体的に。広いほど慎重に・小さく刻む判断材料になる。
- **更新日**: **絶対日付（YYYY-MM-DD）で書く**。「明日」「来週」などの相対表現は使わない
  （後で読むと意味が壊れるため。メモリ規約と同じ方針）。状態を変えたら更新日も更新する。
- **依存**: 順序関係がある項目を明示。これが「次の一手」の根拠になる。

### 記入例（番号と親子）
```
## #6 リッチ型サポート              ← テーマ見出し（本体作業ではない）

## #6a Image / icon
- 状態: 完了
- 優先度: 中
- 影響範囲: framework の Image/Button、生成器
- 更新日: 2026-06-02
- 依存: なし

## #6b Timer
- 状態: 棚上げ
- 優先度: 低
- 影響範囲: Application のイベントループ
- 更新日: 2026-06-02
- 依存: なし

## #7 別の独立作業
- 状態: 未着手
- 優先度: 中
- 影響範囲: ...
- 更新日: 2026-06-02
- 依存: #4          ← 親子ではなく順序依存はここで表す
```

## 難易度の分類軸（任意・領域ごとに定義してよい）
量が多い領域では、項目を**着手コストの段階**で分類しておくと「次の一手」を選びやすい。
分類の刻みは領域が決めてよい。c_api_codegen では次の 3 段を使っている:
- **A**: 既存の仕組みのまま、設定・記述を足すだけで済む（基盤変更ゼロ）。
- **B**: 小さな基盤拡張が要る。
- **C**: 専用の手書き対応が要る。

優先は基本「A（低コストで効果大）から」。ただし実需（live な利用者）があるものを優先する。

## ライフサイクル
1. **起票** — テンプレートで項目を追加。後回し・要検討なら「なぜ / 候補 / 決めること」を埋める。
2. **設計確定** — 作者が「決めること」を確定し、状態を `設計確定` に。
3. **実装中** — 着手したら `実装中`。
4. **完了** — `完了` ＋ 更新日 ＋ 検証結果を記す。**確定した仕様・恒久的な記述は本流のドキュメントへ移し**、
   バックログ側には検討経緯だけ残す（バックログは将来まるごと畳む前提なので、消えて困る情報は移しておく）。
5. **却下** — やらないと決めたら `却下` ＋ 理由。消さずに残す（同じ議論の蒸し返しを防ぐ）。

## 運用ルール
- **意図的な非対応を明記する**: 「できるが、方針としてやらない」ものは理由付きで残す。
  「未着手」と「意図的に外した」を混同しない。
- **先回りで作り込まない（point-of-need）**: 実際に必要になった時点で具体化する。投機的な項目は
  起票しても優先度を低くし、実需が出るまで着手しない。
- **定期的に棚卸しする**: 区切りごとに「やれるのに未着手のもの」を洗い出し、A/B/C と優先度を更新する。
  この棚卸し結果自体も項目（または専用セクション）としてバックログに残す。
- **状態は `状態:` フィールドで表す。打消し線（`~~…~~`）は使わない**。完了・却下は見出しやタイトルを
  消し込まず、`状態: 完了` / `状態: 却下` ＋ 更新日で記録する（状態の二重表現を避ける）。
- **完了項目は履歴として残す**: すぐ消さず、バックログを畳むタイミングでまとめて整理する。
